条款26：避免在万能引用上重载

万能引用参数在重载决议里非常“贪婪”，几乎对什么实参都能形成精确匹配，很容易把本来想调别的重载的调用劫持过去；完美转发构造函数更是重灾区。

2. 一旦加上重载，问题就来了

现在新增一个需求：有些客户只知道名字的整型下标，于是加上一个按 int 重载的版本：

但如果客户手里拿的是 short：

为什么报错？因为有两个重载可选：

  • template<typename T> void logAndAdd(T&&)：T 推导为 short&，形参精确变成 short&，精确匹配。
  • void logAndAdd(int)：需要把 short 整型提升（promotion）成 int。

根据重载决议规则，精确匹配优先于提升转换。于是 logAndAdd(nameIdx) 调了万能引用版本，试图把 short 传给 names.emplace(...) 去构造 std::string，直接编译失败。

当然这时候用static_cast<int>可以解决这个问题

同理，传 std::size_t、long、float 都会被万能引用抢走。

3. 完美转发构造函数是重灾区

把同样的套路搬到构造函数上，问题更隐蔽：

即使你没手写拷贝和移动构造函数，编译器也会自动生成它们，实际上已经构成了重载。看看拷贝一个非 const 的 Person 会发生什么：

直觉上应该调拷贝构造函数，但看看两个候选：

  • 模板构造函数 Person(T&&)：T 推导为 Person&，实例化出 Person(Person&)。
  • 拷贝构造函数 Person(const Person&)：需要对 p 加上 const 限定。

对非 const 左值 p 来说，Person& 比 const Person& 匹配度更高！所以 cloneOfP(p) 调用了完美转发构造函数，试图用一个 Person 对象去初始化 std::string name，编译报错。

此时模板实例化出 Person(const Person&)，和拷贝构造函数签名完全一致。C++ 重载规则规定：当模板实例化函数和普通函数匹配度相同时，优先选普通函数，所以这里才会调拷贝构造。

4. 对继承体系的破坏

如果有子类继承了带完美转发构造函数的 Person：

子类在拷贝/移动构造函数里把 rhs 传给基类 Person，但 rhs 的类型是 SpecialPerson（或 SpecialPerson&&）。

  • 调基类的拷贝/移动构造：需要派生类到基类的隐式转换。
  • 调基类的模板构造 Person(T&&)：T 直接推导为 SpecialPerson& 或 SpecialPerson，精确匹配！

结果子类的拷贝和移动构造函数全部无法编译。

5. 记住

  • 在万能引用上重载，几乎总会让万能引用重载被调用的频率远超你的预期。
  • 完美转发构造函数问题尤其严重：对于非 const 左值，它通常比拷贝构造函数匹配得更好；而且它还会劫持派生类对基类拷贝和移动构造函数的调用。
